# The Economics of AI Agent Model Routing: A Formal Research Methodology for Software Engineering Workloads

## 1. Proposed Academic Title and Abstract

### Proposed Primary Title
**When Does Intelligent Model Routing Pay Off? A Controlled Experimental and Econometric Methodology for Evaluating Human, Heuristic, Learned, and Stage-Aware Model Routers in Autonomous Software Engineering Agents**

### Alternative Short Title
**The Economics of AI Agent Model Routing: A Multi-Policy Experimental Protocol for Software Engineering Workloads**

### Abstract
Autonomous software engineering agents execute multi-turn trajectories involving repository exploration, fault localization, patch synthesis, tool execution, and regression testing. Because language models exhibit wide dispersion in per-token pricing, latency, and reasoning capability, model routing—dynamically assigning requests or trajectory steps to heterogeneous models—is widely hypothesized to reduce inference expenditure without degrading task resolution. However, existing evaluations suffer from four structural defects: reliance on single-turn static prompt benchmarks that ignore stateful agent trajectories and prompt-cache invalidation penalties; conflation of routing algorithms with execution harnesses and model pools; survivorship bias from computing average costs exclusively over resolved tasks; and the absence of rigorous human-intuition and orchestrator-only baselines. This document specifies a standalone, preregistration-ready research methodology to answer a central empirical question: *Does intelligent model routing reduce the total economic cost per independently verified successful task completion across real-world software engineering workloads, and under what task, capability, and pricing conditions does each routing strategy outperform simpler alternatives?* The protocol evaluates eight candidate policy families—explicit human model selection, economical and frontier fixed-model baselines, orchestrator-only delegation, deterministic capability and code-health rules, zero-shot discriminative decision models (such as [TypeSafe Jev](https://openrouter.ai/typesafe/jev-1.14)), semantic and preference-learned routers (such as [RouteLLM](https://github.com/lm-sys/routellm) and [Not Diamond](https://docs.notdiamond.ai/docs/what-is-model-routing)), provider-managed routers (such as [OpenRouter Auto](https://openrouter.ai/openrouter/auto) and [OpenRouter Auto Code](https://openrouter.ai/openrouter/auto-code)), and trajectory-stage or escalation routers (such as [NVIDIA NeMo Switchyard](https://github.com/NVIDIA-NeMo/Switchyard))—under locked execution harnesses ([arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)) and identical candidate model pools. The framework introduces a failure-inclusive econometric accounting model covering four-bucket token billing (fresh input, cache read, cache write, and output/deliberative tokens), routing judge overhead, sandbox compute, retry cascades, and blinded verification, paired with hierarchical generalized linear mixed models, non-parametric superiority estimators ([Kitchenham & Madeyski, 2024](https://www.researchgate.net/publication/383204756_Recommendations_for_analysing_and_meta-analysing_small_sample_size_software_engineering_experiments)), and cost-effectiveness acceptability frontiers.


## 2. Problem Statement and Significance

### 2.1 The Economic Dilemma of Agentic Software Engineering
Modern software engineering agents resolve repository-level issues through iterative closed-loop interactions with compilers, test runners, file systems, and version-control tools ([Jimenez et al., 2024](https://github.com/swe-bench/SWE-bench); [Yang et al., 2024](https://arxiv.org/html/2605.23950v1)). Unlike single-turn question answering, a single software engineering task frequently spans 5 to 50 consecutive model invocations, accumulating tens of thousands to hundreds of thousands of context tokens per trajectory ([TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1); [Prompt-Induced Waste in Coding Agents, arXiv:2608.01347](https://arxiv.org/abs/2608.01347)). Across the contemporary model catalog, per-token prices between economical open-weight or flash-tier models and flagship frontier models span one to two orders of magnitude ($10\times$ to $87\times$ per call), while task resolution rates vary non-monotonically across domains and sub-tasks ([LLMRouterBench, arXiv:2601.07206](https://arxiv.org/html/2601.07206v1); [LangChain Switchyard Benchmark, 2026](https://www.langchain.com/blog/switchyard-agent-routing-benchmark)).

This dispersion creates a fundamental resource allocation problem. Defaulting every agent turn to a frontier model maximizes the probability of resolving complex architectural or debugging bottlenecks but incurs substantial financial expenditure and latency on routine file reads, syntax repairs, and boilerplate edits ([LiteLLM Switchyard Integration, 2026](https://docs.litellm.ai/blog/switchyard-tool-aware-routing)). Conversely, defaulting every turn to an economical model minimizes per-token expenditure but risks trajectory collapse, infinite retry loops, regression introduction, or costly human remediation when a single critical step exceeds the smaller model's capability floor ([TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1); [Triage, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)).

### 2.2 Why Existing Benchmarks Cannot Answer the Economic Question
Although a burgeoning literature proposes automated model routers, current empirical evaluations fail to establish when—or whether—automated routing is economically superior to human intuition, a fixed model, or an informed orchestrator in realistic agentic workflows. Four structural limitations undermine existing claims:

1. **Single-Turn Static Reductionism vs. Stateful Multi-Turn Trajectories:** Foundational benchmarks such as [RouterBench (arXiv:2403.12031)](https://arxiv.org/abs/2403.12031), [RouterArena (arXiv:2510.00202)](https://arxiv.org/abs/2510.00202), and [LLMRouterBench (arXiv:2601.07206)](https://arxiv.org/html/2601.07206v1) evaluate routing as a one-shot mapping from an isolated prompt to a pre-computed static outcome matrix. Even where [LLMRouterBench](https://arxiv.org/html/2601.07206v1) incorporates 500 [SWE-bench](https://github.com/swe-bench/SWE-bench) instances, it reduces them to zero-shot single-query generations without an agent scaffold or intermediate tool calls. In live multi-turn agents, the prefix at step $i+1$ is causally shaped by the action and tool output at step $i$; a premature downgrade at step $i$ can corrupt the repository state and cause irreversible trajectory failure even if steps $i+1 \dots N$ use a frontier model ([TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)).
2. **Neglect of Prompt Caching and Switching Friction:** In multi-turn coding sessions, up to 90–95% of input tokens at turn $t$ repeat the prefix from turn $t-1$. Major providers discount cached prefix reads (`cache_read`) by 75–90% relative to fresh input tokens, while charging full input rates or a $1.25\times$ premium (`cache_write`) when building a new cache ([TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)). Switching models mid-session invalidates the warm prompt cache on the prior model endpoint, forcing a cold cache rebuild on the incoming model ([OpenRouter Auto and Auto Code Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)). Step-level routers that ignore cache state can increase realized API bills even when selecting nominally cheaper per-token models.
3. **Unaccounted Routing Overhead and Survivorship Bias:** Automated routers introduce direct economic and latency overheads—such as auxiliary LLM-judge invocations that consumed 21.2% of total routed expenditure in the [LangChain NeMo Switchyard study](https://www.langchain.com/blog/switchyard-agent-routing-benchmark)—and indirect costs from misrouting-induced failures. Studies that compute "average cost per solved task" by averaging only over successful trajectories commit survivorship bias, treating burned tokens on failed trajectories as free ([TwinRouterBench Appendix A.15, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)).
4. **Ontological Conflation of Algorithm, Implementation, and Architecture:** Vendor announcements and academic comparisons frequently pit a router operating over a 600-model catalog with proprietary provider-failover logic against a binary classifier restricted to two models, or compare scores across different agent harnesses. As demonstrated by [Zhang et al. (2026, arXiv:2605.23950)](https://arxiv.org/html/2605.23950v1) and the [Holistic Agent Leaderboard (HAL, arXiv:2510.11977)](https://arxiv.org/abs/2510.11977), varying the execution harness while holding the model fixed shifts [SWE-bench Verified](https://www.swebench.com/verified.html) and [SWE-Bench Pro](https://arxiv.org/pdf/2509.16941) resolution rates by 9.5 to 48 percentage points—dwarfing the 2 to 5 percentage point differences typically attributed to routing algorithms.

### 2.3 Ontological Distinction: Algorithm vs. Implementation vs. Execution Architecture
To prevent category errors and methodological circularity, this study enforces a strict three-layer ontological separation across all candidate policies:

| Ontological Layer | Formal Definition | Primary Control / Experimental Treatment | Representative Examples |

### 2.4 Core Position and Scope neutrality
This methodology adopts a strictly falsificationist, vendor-neutral stance: **there may be no universally optimal router**. Whether a routing strategy reduces total economic cost per verified completion is a conditional empirical question governed by task difficulty distributions, inter-tier price ratios, prompt-cache persistence, verification gate strictness, and human or orchestrator baseline competence. A negative or null finding—demonstrating that a well-chosen fixed model, a simple deterministic rule, or documented human developer intuition outperforms complex learned or commercial routers across specific regimes—constitutes a first-class scientific contribution of equal publication value to a positive finding.


## 3. Systematic Literature Review Protocol

To ground the experimental design in cumulative scientific evidence and prevent redundant benchmarking, Phase 1 of the research program executes a formal Systematic Literature Review (SLR) adhering to the [PRISMA 2020 reporting statement (Page et al., 2021)](https://www.bmj.com/content/372/bmj.n71), the [Evidence-Based Software Engineering (EBSE) guidelines (Kitchenham & Charters, 2007)](https://www.researchgate.net/publication/302924724_Guidelines_for_performing_Systematic_Literature_Reviews_in_Software_Engineering), and bidirectional citation snowballing ([Wohlin, 2014](https://www.wohlin.eu/ease14.pdf)).

### 3.1 Information Sources and Database Coverage
Because model routing research spans peer-reviewed machine learning venues, software engineering conferences, fast-moving arXiv preprints, open-source infrastructure repositories, and commercial gateway releases, the search protocol queries eight complementary indices across the window from **January 1, 2022 through November 8, 2026**:

1. **Formal Bibliographic Databases:** ACM Digital Library, IEEE Xplore, Scopus, and Clarivate Web of Science (Core Collection).
2. **Preprint and Open Peer-Review Archives:** [arXiv.org](https://arxiv.org/) (`cs.SE`, `cs.AI`, `cs.CL`, `cs.LG`) and [OpenReview.net](https://openreview.net/) (ICLR, NeurIPS, ICML, TMLR submissions, including rejected and withdrawn papers to mitigate publication bias against negative routing results).
3. **Programmatic Scholarly Aggregators:** [Semantic Scholar API](https://www.semanticscholar.org/) and DBLP Computer Science Bibliography.
4. **Open-Source Code and Grey Literature Repositories:** GitHub repositories (via GitHub Search API filtering by topic `llm-routing`, `model-router`, `coding-agent`), Hugging Face Papers/Datasets ([Hugging Face Papers](https://huggingface.co/papers)), and primary engineering blogs/documentation from infrastructure providers ([OpenRouter Blog](https://openrouter.ai/blog/), [NVIDIA Developer Technical Blog](https://developer.nvidia.com/blog/route-ai-agent-workloads-across-models-with-nvidia-nemo-switchyard/), [LangChain Blog](https://www.langchain.com/blog/switchyard-agent-routing-benchmark), [LiteLLM Blog](https://docs.litellm.ai/blog/switchyard-tool-aware-routing), [Not Diamond Docs](https://docs.notdiamond.ai/docs/what-is-model-routing), and [Holistic Agent Leaderboard](https://hal.cs.princeton.edu/)).

### 3.2 Reproducible Search Strings
Search queries are structured into three conjunctive facets—**Target System (LLM/Agent)**, **Intervention (Routing/Cascading/Selection)**, and **Outcome/Domain (Cost/Economics/Software Engineering)**—calibrated against a known gold-standard start set ([FrugalGPT, arXiv:2305.05176](https://arxiv.org/abs/2305.05176); [HybridLLM, GitHub](https://github.com/microsoft/best-route-llm); [RouteLLM, arXiv:2406.18665](https://arxiv.org/pdf/2406.18665); [RouterBench, arXiv:2403.12031](https://arxiv.org/abs/2403.12031); [LLMRouterBench, arXiv:2601.07206](https://arxiv.org/html/2601.07206v1); [TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1); [Triage, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)).

### 3.3 Inclusion and Exclusion Criteria
Every retrieved record undergoes two-stage screening (Title/Abstract followed by Full-Text review) against explicit eligibility criteria:

* **Inclusion Criteria (IC):**
  * **IC1 (Routing Mechanism):** Proposes, formalizes, or empirically evaluates a mechanism that selects among $\ge 2$ distinct language models or reasoning-effort configurations at inference time (pre-task, per-query, per-step, or via sequential cascade/escalation).
  * **IC2 (Economic or Efficiency Dimension):** Reports or models at least one resource metric (monetary API cost, token consumption, compute/GPU-hours, cache read/write rates, or latency) alongside a task-quality or resolution metric.
  * **IC3 (Agentic or Software Engineering Relevance):** Evaluates multi-turn agentic workflows, tool-calling trajectories, or software engineering/code-generation tasks, *or* introduces a foundational routing algorithm/benchmark directly transferable to agentic routing.
  * **IC4 (Verifiable Artifact or Specification):** Provides mathematical formulation, executable open-source code, public dataset/trace logs, or documented API specifications sufficient to classify its input signals and decision logic.
* **Exclusion Criteria (EC):**
  * **EC1 (Internal Mixture-of-Experts Only):** Studies exclusively addressing sub-token internal neural routing within a single model's Mixture-of-Experts (MoE) feed-forward layers (e.g., Switch Transformer token-to-expert gating) without cross-model or inference-effort selection.
  * **EC2 (Network/Packet Routing):** Traditional computer networking, hardware interconnect, or wireless packet routing papers using ML.
  * **EC3 (Zero-Evidence Marketing Claims):** Vendor blog posts, social media threads, or press releases asserting percentage cost savings without disclosing the benchmark corpus, candidate model pool, or scoring methodology (unless included strictly as a grey-literature subject of critical appraisal under Tier D evidence).
  * **EC4 (Duplicate / Superseded Preprints):** Earlier arXiv versions superseded by a peer-reviewed conference/journal version or a more recent substantive revision (both versions are linked for provenance, but data extraction uses the canonical latest version).

### 3.4 Citation-Chaining (Snowballing) and Inter-Rater Reliability
Following [Wohlin (2014)](https://www.wohlin.eu/ease14.pdf), once the initial database screening establishes the **Start Set**, researchers execute iterative backward snowballing (inspecting reference lists of all included studies) and forward snowballing (querying [Semantic Scholar](https://www.semanticscholar.org/) and Google Scholar for all works citing the Start Set). Iterations continue until an entire pass yields zero newly included studies. Two independent reviewers screen a stratified random sample of 20% of candidate records; screening rubrics require a minimum Cohen's kappa ($\kappa \ge 0.80$) before single-reviewer screening proceeds, with all borderline cases resolved by a third adjudicator.

### 3.5 Evidence Grading Rubric and Treatment of Recent Vendor Leads
To prevent unverified vendor claims from polluting the scientific baseline, every source in the literature review is assigned an explicit **Evidence Tier (Tier A through Tier D)** adapted from software engineering evidence hierarchies ([Kitchenham & Charters, 2007](https://www.researchgate.net/publication/302924724_Guidelines_for_performing_Systematic_Literature_Reviews_in_Software_Engineering)) and GRADE principles:

| Evidence Tier | Classification Criteria | Methodological Role in This Study |
| :--- | :--- | :--- |
| **Tier A: High-Rigor Empirical & Reproducible** | Peer-reviewed papers or preprints with public code, locked model pools, multi-seed/multi-run variance reporting, failure-aware cost accounting, and execution-verified labels (e.g., [TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1); [LLMRouterBench, arXiv:2601.07206](https://arxiv.org/html/2601.07206v1); [Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1); [Prompt-Induced Waste, arXiv:2608.01347](https://arxiv.org/abs/2608.01347); [RouteLLM, arXiv:2406.18665](https://arxiv.org/pdf/2406.18665)). | Used to parameterize priors, variance decompositions, cost equations, and statistical power simulations. |
| **Tier B: Methodological / Observational Academic** | Peer-reviewed or preprint studies with sound theoretical formulation or single-shot empirical evaluation, but lacking live multi-turn agent execution, cache accounting, or full open-source artifacts (e.g., [FrugalGPT, arXiv:2305.05176](https://arxiv.org/abs/2305.05176); [AutoMix, arXiv:2310.12963](https://arxiv.org/abs/2310.12963); [Triage, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1); [SharedTrunkNet, arXiv:2603.20895](https://arxiv.org/html/2603.20895v2)). | Used to define candidate routing algorithms, feature spaces, and theoretical break-even conditions. |
| **Tier C: Instrumented Engineering Reports** | Technical reports from engineering teams that disclose harness configs, model pairings, run counts, and raw accuracy/cost tables, but without independent peer review (e.g., [LangChain NeMo Switchyard Benchmark, Aug 11, 2026](https://www.langchain.com/blog/switchyard-agent-routing-benchmark); [OpenRouter Jev Technical Guide, Oct 16, 2026](https://openrouter.ai/blog/insights/what-is-jev/)). | Used to configure candidate implementations and identify practical confounders (e.g., judge token tax, strike confirmation counts). |
| **Tier D: Unvalidated Vendor Announcements** | Commercial product launch posts, model cards, and vendor-hosted leaderboards where the underlying decision weights, benchmark instances, or counterfactual runs are proprietary or undisclosed (e.g., [OpenRouter Auto & Auto Code Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/); [Not Diamond Commercial Docs](https://docs.notdiamond.ai/docs/what-is-model-routing)). | Treated strictly as **testable hypotheses and black-box experimental subjects**, never as established empirical truth. |

#### Critical Appraisal of the November 6, 2026 OpenRouter Auto and Auto Code Lead
On November 6, 2026, OpenRouter announced a rebuilt generation of its general-purpose router (`openrouter/auto`) alongside a new coding-specialized router (`openrouter/auto-code`, released November 5, 2026 on its model page) ([OpenRouter Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/); [OmniaKey Independent Review, Nov 7, 2026](https://omniakey.com/blog/openrouter-auto-router-vs-auto-code)). The vendor announcement reports several notable architectural mechanisms and performance claims:
* **Reported Architectural Mechanisms:** A fast decision model evaluates 11 request factors in a single call (task type, task-shift detection, estimated difficulty, latency sensitivity, vision/codebase requirements, and whether a larger model, higher `reasoning_effort`, or cheaper model is appropriate) and combines them with live provider pricing, provider health, and prompt-cache status ([OpenRouter Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)). Crucially, `openrouter/auto-code` is designed for coding harnesses: it starts in a higher cost tier, penalizes test failures and repeated identical errors by escalating or switching models sooner, and protects prompt-caching economics by preferring adjustments in `reasoning_effort` over model switches (reportedly staying on the same warm model for nearly 9 out of 10 agent turns during beta testing) ([OpenRouter Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/); [OmniaKey, Nov 7, 2026](https://omniakey.com/blog/openrouter-auto-router-vs-auto-code)). Furthermore, the announcement indicates that production verification utilized [`typesafe/jev-router`](https://openrouter.ai/typesafe/jev-router) and `openrouter/auto-beta` ([OpenRouter Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)).
* **Unvalidated Vendor Claims Requiring Independent Falsification:** OpenRouter claims that (a) the rebuilt router outperforms its legacy router by up to $4\times$ depending on the benchmark; (b) p90 routing step latency dropped $3\times$ from 1.96s to 0.65s; (c) across five internal benchmarks, `openrouter/auto-code` "scores in line with Claude Opus 5.5 while costing 74% less per task"; and (d) invalid tool calls dropped $4\times$ and cut-off agentic responses dropped by $50\%$ in beta ([OpenRouter Announcement, Nov 6, 2026](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)). Under the evidence-grading protocol, these claims are graded **Tier D**: the specific task instances, harness configurations, failure-penalty accounting formulas, and candidate model pools are not independently auditable, and earlier independent evaluation on [LLMRouterBench (arXiv:2601.07206)](https://arxiv.org/html/2601.07206v1) found that legacy `openrouter/auto` underperformed the best single model by 24.7 percentage points and failed to support tool-calling on $\tau^2$-Bench. Consequently, the experimental design treats `openrouter/auto` and `openrouter/auto-code` as priority experimental arms tested under both **Pool-Restricted Parity** (via `allowed_models` locked to the exact same candidate pool as open-source routers) and **Native Catalog Mode** (to isolate algorithm quality from catalog breadth).

## 5. Research Gaps and Novelty Assessment

A skeptical examination of the prior-art matrix reveals that while substantial progress has been made on single-turn query routing ([RouteLLM, arXiv:2406.18665](https://arxiv.org/pdf/2406.18665); [LLMRouterBench, arXiv:2601.07206](https://arxiv.org/html/2601.07206v1)) and initial step-level benchmarks ([TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)), **seven critical research gaps** remain unresolved in the literature:

1. **Gap 1 — Absence of Controlled Human-Intuition Baselines:** In daily software engineering practice, developers manually select a model and reasoning effort in their IDE or CLI harness (e.g., picking a fast economical model for a CSS/config tweak and a high-effort frontier model for a concurrency bug). No published routing benchmark compares automated routers against **explicit, documented human developer intuition** operating under identical task information and model pools. Without this baseline, the field cannot tell whether automated routers add value over normal developer judgment.
2. **Gap 2 — Unresolved Trade-off Between Orchestrator-Only Delegation and Dedicated Routers:** Modern agent harnesses increasingly employ a frontier orchestrator that decomposes a task and dispatches scoped sub-tasks to worker sub-agents. Whether an external dedicated router (such as [TypeSafe Jev](https://openrouter.ai/typesafe/jev-1.14), [RouteLLM](https://github.com/lm-sys/routellm), or [NeMo Switchyard](https://github.com/NVIDIA-NeMo/Switchyard)) reduces total cost relative to an **informed orchestrator** that natively assigns worker model tiers during task decomposition has not been tested under controlled harness parity.
3. **Gap 3 — Untested Efficacy of Zero-Shot "System One" Decision Models vs. Supervised Routers:** Discriminative decision models ([TypeSafe Jev 1.14](https://openrouter.ai/typesafe/jev-1.14)) offer ultra-low decision cost ($\$0.042/\text{1M}$ input tokens, $\$0$ output) and calibrated probability distributions without task-specific training ([OpenRouter Jev Guide](https://openrouter.ai/blog/insights/what-is-jev/)). However, [TwinRouterBench (arXiv:2605.18859)](https://arxiv.org/html/2605.18859v1) demonstrated that zero-shot prompting of a frontier generative model (Claude Opus 4.6) failed catastrophically as a step-level router on SWE-bench (under-predicting 95.2% of high-tier steps), whereas a lightweight logistic classifier trained on execution-verified labels cut costs by 53.1%. Whether zero-shot calibrated System One models suffer from the same uncalibrated optimism on software engineering prefixes as generative LLM judges—or whether they match supervised routers—is entirely unknown.
4. **Gap 4 — Task-Level Pre-Dispatch vs. Mid-Trajectory Stage/Escalation Routing:** Task-level routing ([Triage, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)) preserves 100% of within-session prompt-cache locality and avoids mid-trajectory model-switching friction, whereas step-level/stage-aware routing ([NeMo Switchyard](https://docs.litellm.ai/blog/switchyard-tool-aware-routing); [TwinRouterBench](https://arxiv.org/html/2605.18859v1)) adapts dynamically to test failures and exploration vs. implementation phases at the risk of cache invalidation and cross-model stylistic drift. No study has conducted a head-to-head factorial comparison of task-level, stage-aware, and escalation routing on the same dynamic coding benchmark with full cache-write accounting.
5. **Gap 5 — Independent Validation of Next-Generation Provider-Managed Coding Routers:** The November 6, 2026 release of [OpenRouter Auto Code](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/) introduces cache-preserving `reasoning_effort` modulation prior to model switching. No independent, peer-reviewed evaluation has tested `openrouter/auto-code` against open-source routers under locked model pools, nor decomposed how much of its performance stems from its routing policy versus its underlying provider-routing and catalog access.
6. **Gap 6 — Survivorship-Unbiased Full Economic Accounting (API vs. Subscription Quotas):** Existing studies largely ignore the economic interaction between verification gates (unit test suites vs. imperfect lint/type checks), retry loops, human code-review remediation costs for subtle regressions, and the structural difference between **marginal API billing** and **rate-limited subscription quotas**.
7. **Gap 7 — Harness-Router Interaction Effects:** [Zhang et al. (2026, arXiv:2605.23950)](https://arxiv.org/html/2605.23950v1) and [Prompt-Induced Waste (arXiv:2608.01347)](https://arxiv.org/abs/2608.01347) prove that harness mechanics (context compression, tool schema verbosity, verification hooks) dominate single-model variance and flip model rankings. Whether optimal routing policies remain invariant across distinct harness controllers ($H_{\text{minimal}}$ vs. $H_{\text{full}}$) has never been evaluated.


## 6. Research Questions and Falsifiable Hypotheses

To address these gaps with doctoral-committee rigor, the methodology formulates eight research questions (RQ1–RQ8) paired with formal, falsifiable hypotheses (H1–H8). Let $\text{TEC}_{\text{succ}}(\pi)$ denote the **Total Economic Cost per Independently Verified Successful Completion** for policy $\pi$ (formally defined in Section 8.3), $P_{\text{succ}}(\pi)$ denote the independently verified task resolution probability, and $\text{Bill}_j(\pi) = C_j(\pi) + (1 - Y_j(\pi))\gamma$ denote the failure-penalized per-instance economic bill on task $j$ with remediation penalty $\gamma$.

### RQ1: Routing vs. No Routing (Fixed-Model Baselines)
* **Question:** Under what task difficulty distributions and inter-tier price ratios does any intelligent routing policy achieve a statistically and practically significant reduction in $\text{TEC}_{\text{succ}}$ without degrading $P_{\text{succ}}$ beyond a pre-specified non-inferiority margin $\delta$ relative to the best fixed model (`P2b_FixedFrontier` or `P2a_FixedEcon`)?
* **Hypothesis H1 (Conditional Routing Advantage):** A routing policy $\pi$ strictly dominates both fixed baselines ($\text{TEC}_{\text{succ}}(\pi) < \min\{\text{TEC}_{\text{succ}}(\text{FixedFrontier}), \text{TEC}_{\text{succ}}(\text{FixedEcon})\}$ with $P_{\text{succ}}(\pi) \ge P_{\text{succ}}(\text{FixedFrontier}) - \delta$) **if and only if** three conditions hold jointly: (i) the workload exhibits non-degenerate **model disagreement headroom** $\Delta P = P_{\text{succ}}(\text{FixedFrontier}) - P_{\text{succ}}(\text{FixedEcon}) \ge 0.10$; (ii) the frontier-to-economical realized trajectory cost ratio satisfies $\kappa = \bar{C}_{\text{Frontier}} / \bar{C}_{\text{Econ}} > (1 - p_{\text{offload}} \cdot (1 - f_{\text{misroute}}))^{-1}$; and (iii) the router's recall on verified high-tier tasks exceeds $1 - \delta / \Delta P$.
* **Measurable Variables:** Per-instance resolution $Y_j \in \{0,1\}$, realized trajectory cost $C_j$, inter-tier cost ratio $\kappa$, workload disagreement fraction ([Varshney et al., arXiv:2603.20895](https://arxiv.org/html/2603.20895v2)), high-tier recall, and $\text{TEC}_{\text{succ}}$.
* **Plausible Counterexamples:** On saturated workloads where an economical model resolves $\ge 92\%$ of tasks that a frontier model resolves (as observed in the 8 pp spread on the [LangChain Deep Agents suite](https://www.langchain.com/blog/switchyard-agent-routing-benchmark)), `P2a_FixedEcon` achieves lower $\text{TEC}_{\text{succ}}$ than any router; conversely, on uniformly hard architectural tasks where economical models have $<10\%$ success, `P2b_FixedFrontier` beats all routers due to zero misrouting/cache-switch overhead.
* **Falsification Condition:** H1 is falsified if a router significantly reduces $\text{TEC}_{\text{succ}}$ when $\Delta P < 0.05$ or $\kappa < 1.5$, or if no evaluated router beats $\min\{\text{TEC}_{\text{succ}}(\text{FixedFrontier}), \text{TEC}_{\text{succ}}(\text{FixedEcon})\}$ by at least the Minimum Practically Significant Effect Size ($\text{MPSES} = 10\%$ cost reduction at $\delta = 0.03$ non-inferiority) on heterogeneous mixed-difficulty workloads.

### RQ2: Human Judgment vs. Automated Classification
* **Question:** How does explicit, documented human developer model selection (`P1_Human`) compare in $\text{TEC}_{\text{succ}}$, $P_{\text{succ}}$, and decision time cost against automated pre-task and step-level routers when both are restricted to the identical candidate model pool?
* **Hypothesis H2 (Human Repository-Context Advantage vs. Time Tax):** When human software engineers possess prior familiarity with the target repository or inspect file-level localization cues (`P1b_HumanRepoAware`), their raw API inference cost per resolved task ($\text{API-TEC}_{\text{succ}}$) will be non-inferior to or lower than zero-shot automated classifiers (`P4_DetRules`, `P5_DiscClassifier`) because humans accurately identify architectural blast radius; however, when human decision latency ($t_{\text{human}}$ seconds at wage rate $w_{\text{eng}}$) is priced into $\text{TEC}_{\text{succ}}$, automated routers outperform `P1_Human` on routine and medium-complexity issues where human triage time exceeds the API cost differential.
* **Measurable Variables:** Human selection choice $(m_j, e_j)$, human decision duration $t_{\text{human},j}$ (seconds), self-reported confidence and rationale tags, $\text{API-TEC}_{\text{succ}}$ (excluding human triage labor), and fully loaded $\text{TEC}_{\text{succ}}$ (including $w_{\text{eng}} \cdot t_{\text{human},j}$).
* **Plausible Counterexamples:** Developers systematically over-provision frontier models out of risk aversion ("Opus default bias"), causing `P1_Human` to underperform automated routers even on raw API spend; or developers systematically under-estimate hidden cross-file test dependencies, causing high failure rates.
* **Falsification Condition:** H2 is falsified if automated zero-shot routers (`P4` or `P5`) achieve lower raw $\text{API-TEC}_{\text{succ}}$ and higher high-tier recall than `P1b_HumanRepoAware` at $p < 0.05$, or if `P1_Human` remains cheaper than automated routing even after pricing human decision latency at standard senior engineering rates ($\$100\text{--}\$150/\text{hr}$).

### RQ3: Orchestrator-Only Delegation vs. Dedicated Routing
* **Question:** Does a dedicated external routing layer (`P5`–`P8`) reduce total cost per verified completion compared to an orchestrator-only architecture (`P3_Orchestrator`) in which a frontier planning model decomposes the issue and natively assigns model tiers to sub-tasks?
* **Hypothesis H3 (Orchestration Overhead vs. Sub-Task Specialization):** On single-file and localized multi-file bugs (Complexity Strata S1–S2), dedicated lightweight routers (`P5_DiscClassifier`, `P6_LearnedRouter`, `P8_StageEscalation`) achieve lower $\text{TEC}_{\text{succ}}$ than `P3_Orchestrator` because the frontier orchestrator's planning and context-handoff token overhead exceeds the worker-tier savings (consistent with multi-agent token multiplication findings in [Prompt-Induced Waste, arXiv:2608.01347](https://arxiv.org/abs/2608.01347)); conversely, on decomposable cross-module refactoring tasks (Stratum S4), `P3_Orchestrator` outperforms single-agent routed trajectories by isolating worker context windows and preventing context drift.
* **Measurable Variables:** Orchestrator planning tokens, sub-agent handoff tokens, total trajectory tokens, context drift rate $\delta_t$ ([Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)), and $\text{TEC}_{\text{succ}}$ across complexity strata S1–S4.
* **Plausible Counterexamples:** Dedicated stage-aware routing inside a single agent (`P8_StageEscalation`) outperforms `P3_Orchestrator` across all strata including S4 because sub-agent handoffs lose implicit repository context and incur duplicate file-reading tool calls.
* **Falsification Condition:** H3 is falsified if `P3_Orchestrator` achieves lower $\text{TEC}_{\text{succ}}$ than dedicated routers on S1–S2 tasks, or if single-agent routed policies beat `P3_Orchestrator` on S4 decomposable refactoring tasks.

### RQ4: Generic Zero-Shot Classifiers vs. Learned Performance Predictors
* **Question:** Do supervised performance predictors trained on execution-verified software engineering outcomes (`P6_LearnedRouter`, e.g., [RouteLLM](https://github.com/lm-sys/routellm), [Not Diamond custom](https://docs.notdiamond.ai/docs/router-training-quickstart), [TwinRouterBench logistic router](https://arxiv.org/html/2605.18859v1), [SharedTrunkNet prefill MLP](https://arxiv.org/html/2603.20895v2)) outperform deterministic rules (`P4_DetRules`) and zero-shot discriminative decision models (`P5_DiscClassifier`, e.g., [TypeSafe Jev 1.14](https://openrouter.ai/typesafe/jev-1.14))?
* **Hypothesis H4 (Supervision Necessity for Capability Boundaries):** Zero-shot discriminative classifiers (`P5_DiscClassifier`) and deterministic code-health rules (`P4_DetRules`) capture coarse surface complexity but systematically misestimate model-specific failure boundaries on deceptive software engineering steps (echoing the 95.2% high-tier under-prediction by uncalibrated zero-shot LLM routing in [TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)). Consequently, routers calibrated or trained on execution-verified repository traces (`P6_LearnedRouter`) achieve significantly higher trajectory pass rates (`TrajPass`) and lower $\text{TEC}_{\text{succ}}$ on in-distribution model pools, whereas `P4_DetRules` and `P5_DiscClassifier` exhibit superior zero-shot transfer when candidate models are swapped without retraining.
* **Measurable Variables:** Step-level Brier score and ROC-AUC ([Varshney et al., arXiv:2603.20895](https://arxiv.org/html/2603.20895v2)), high-tier recall, under-triage rate ($P(\tilde{t}_i < \hat{t}_i)$), over-triage rate ($P(\tilde{t}_i > \hat{t}_i)$), `TrajPass`, and $\text{TEC}_{\text{succ}}$.
* **Plausible Counterexamples:** [TypeSafe Jev 1.14](https://openrouter.ai/typesafe/jev-1.14) with thresholded `Score`/`Choice` confidence bands and explicit repository-metadata state fields matches the `TrajPass` and $\text{TEC}_{\text{succ}}$ of supervised `P6_LearnedRouter` without requiring any offline training corpus.
* **Falsification Condition:** H4 is falsified if zero-shot `P5_DiscClassifier` or `P4_DetRules` achieves non-inferior or lower $\text{TEC}_{\text{succ}}$ and $\le 3$ pp difference in high-tier recall compared to supervised `P6_LearnedRouter` on the held-out in-distribution test split.

### RQ5: Task-Level Dispatch vs. Execution-Stage and Escalation Routing
* **Question:** Does dynamic mid-trajectory routing (`P8_StageEscalation` via tool-trajectory stage routing or failure-triggered escalation, and `P7_ProviderManaged` via `openrouter/auto-code`) outperform static pre-task routing (`P4`–`P6` invoked once at $t=0$) once prompt-cache invalidation (`cache_write`) and cross-model handoff friction are fully priced?
* **Hypothesis H5 (The Cache-Switch Friction Trade-off):** Naive per-step routing that switches models without cache-state hysteresis degrades net savings relative to task-level routing due to repeated `cache_write` penalties ($10\times\text{--}12.5\times$ `cache_read` rates on frontier tiers; [TwinRouterBench Table A5](https://arxiv.org/html/2605.18859v1)) and tool-format drift. However, **cache-aware stage/escalation routing**—which holds model affinity during routine exploration/editing, modulates `reasoning_effort` on the warm model first ([OpenRouter Auto Code](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)), and escalates to a held frontier model (`capable_hold`) only upon observable tool/test failures ([LiteLLM Switchyard Stage Router](https://docs.litellm.ai/blog/switchyard-tool-aware-routing))—achieves lower $\text{TEC}_{\text{succ}}$ than both static task-level routing (which cannot recover from initial under-triage without restarting the entire task) and memoryless per-step routing.
* **Measurable Variables:** Number of model switches per trajectory $N_{\text{switch}}$, cache hit ratio $\text{CHR} = n^{\text{cr}} / (n^{\text{in}} + n^{\text{cr}} + n^{\text{cw}})$, `cache_write` expenditure $C_{\text{cw}}$, recovery rate within $k$ steps of a tool/test failure $RR(k)$ ([Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)), and $\text{TEC}_{\text{succ}}$.
* **Plausible Counterexamples:** Task-level routing with a single verification-gate fallback retry ([Triage Eq. 1, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)) is cheaper and more reliable than mid-trajectory escalation because starting fresh with a frontier model on a clean context avoids inheriting a polluted, error-ridden trajectory prefix from a weaker model.
* **Falsification Condition:** H5 is falsified if static task-level routing with clean-context fallback achieves lower $\text{TEC}_{\text{succ}}$ and higher $P_{\text{succ}}$ than cache-aware stage/escalation routing (`P8_StageEscalation` and `P7_ProviderManaged`).

### RQ6: Routing Overhead and Break-Even Economics
* **Question:** Under what analytical and empirical conditions does the fixed and variable overhead of the router itself (classifier/judge tokens, latency, infrastructure, and misrouting retries) exceed the gross inference savings from offloading calls?
* **Hypothesis H6 (The Judge-Tax and Offload Break-Even Bound):** Extending the [LangChain Switchyard offload bound](https://www.langchain.com/blog/switchyard-agent-routing-benchmark) and [Triage fallback equation (arXiv:2604.07494)](https://arxiv.org/html/2604.07494v1) to include prompt-cache invalidation and failure retries, a router breaks even against an always-frontier baseline ($\mathbb{E}[C(\pi)] < \mathbb{E}[C(\text{Frontier})]$) if and only if the realized offload fraction $r_{\text{off}}$ satisfies:
  $$r_{\text{off}} > \frac{C_{\text{router}} + p_{\text{switch}} \cdot \Delta C_{\text{cache}}}{(\bar{c}_{\text{Frontier}} - \bar{c}_{\text{Econ}}) - f_{\text{misroute}} \cdot \bar{c}_{\text{retry}}}$$
  Consequently, LLM-as-a-judge routers (where $C_{\text{router}}$ scales with un-cached trajectory prefix length, reaching $>20\%$ of total spend in [LangChain, 2026](https://www.langchain.com/blog/switchyard-agent-routing-benchmark)) fail to break even whenever the inter-model price gap narrows below $3\times$ or $f_{\text{misroute}} > 0.25$, whereas constant-overhead routers (deterministic rules `P4`, embedding/MLP routers `P6`, and $\$0.042/\text{1M}$ System One models `P5`) remain economically viable down to a $1.5\times$ price gap.
* **Measurable Variables:** Router overhead $C_{\text{router}}$, switch probability $p_{\text{switch}}$, cache rebuild penalty $\Delta C_{\text{cache}}$, misrouting fallback rate $f_{\text{misroute}}$, and empirical break-even threshold across simulated price ratios.
* **Plausible Counterexamples:** Even zero-cost routers (`P4_DetRules`) fail to break even at a $10\times$ price gap because their misrouting rate $f_{\text{misroute}}$ triggers long, expensive frontier recovery trajectories ($\bar{c}_{\text{retry}} > 1.5 \bar{c}_{\text{Frontier}}$).
* **Falsification Condition:** H6 is falsified if empirical net savings deviate systematically from the structural break-even inequality or if LLM-judge routers achieve lower $\text{TEC}_{\text{succ}}$ than constant-overhead routers when $\bar{c}_{\text{Frontier}} / \bar{c}_{\text{Econ}} \le 3$.

### RQ7: Capability Floors and Verification Gate Quality
* **Question:** How does the strictness and coverage of the automated verification gate (comprehensive unit test suite vs. weak/incomplete tests vs. syntax/linter-only checks) alter the optimal routing strategy and the incidence of silent regressions ("pseudo-passes")?
* **Hypothesis H7 (Verification Gate Asymmetry):** When the verification gate has high test coverage and mutation score ([UTBoost, arXiv:2506.09289](https://casrai.org/guides/swe-bench)), aggressive optimistic routing (starting on economical tiers and escalating on test failure, as in `P8_StageEscalation` and `P4_Triage`) minimizes $\text{TEC}_{\text{succ}}$ because false passes are caught deterministically before submission. Conversely, when repository test coverage of modified files is low ($<50\%$) or absent, optimistic routing produces a surge in **false-positive submissions** (patches that pass existing weak tests or linters but fail independent held-out tests or human code review), causing conservative frontier-first routing (`P2b_FixedFrontier` or high-threshold `P6_LearnedRouter`) to win once post-submission verification and human remediation costs are included.
* **Measurable Variables:** Pre-submission test pass rate, post-submission held-out test pass rate ([SWE-bench Plus / UTBoost](https://casrai.org/guides/swe-bench)), silent regression rate $\text{SRR} = P(\text{Pass}_{\text{harness}} = 1 \wedge \text{Pass}_{\text{independent}} = 0)$, and $\text{TEC}_{\text{succ}}$ under full vs. ablated test suites.
* **Plausible Counterexamples:** Stage-aware routers that inspect tool execution errors (compiler/linter/AST signals) maintain low $\text{SRR}$ even when unit tests are ablated.
* **Falsification Condition:** H7 is falsified if the ranking of optimistic escalation routers versus conservative routers on $\text{TEC}_{\text{succ}}$ remains invariant when repository test suites are experimentally ablated to linter-only verification.

### RQ8: Generalizability Across Task Distributions, Harnesses, and Model Catalogs
* **Question:** Do routing policies and learned router weights generalize across (a) unseen software repositories and programming languages, (b) distinct execution harnesses ($H_{\text{minimal}}$ vs. $H_{\text{full}}$ per [Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)), and (c) temporal shifts in the candidate model catalog and provider pricing?
* **Hypothesis H8 (Harness-Router Coupling and Catalog Drift):** Following the Binding Constraint Thesis ([Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)) and [Prompt-Induced Waste (arXiv:2608.01347)](https://arxiv.org/abs/2608.01347), routing performance interacts strongly with the execution harness ($\text{Var}(\text{Router} \times \text{Harness}) > 0$): a closed-loop harness with compressed retrieval context and structured error feedback ($H_2/H_3$) raises the effective capability floor of economical models, shifting the optimal routing threshold toward cheaper tiers compared to an open-loop minimal harness ($H_1$). Furthermore, model-ID-bound learned routers (`P6` trained on static model labels) degrade significantly under catalog substitution without re-labeling, whereas tier-abstracted routers ([TwinRouterBench tier pools, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1); [Triage, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)), mechanistic prefill routers ([SharedTrunkNet, arXiv:2603.20895](https://arxiv.org/html/2603.20895v2)), and live-telemetry provider routers (`P7_ProviderManaged`) degrade less under catalog updates.
* **Measurable Variables:** Out-of-distribution (OOD) repository $\text{TEC}_{\text{succ}}$, harness-by-router interaction variance $\sigma^2_{RH}$ and ranking reversal count ([Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)), and performance retention after holding out one model per tier and substituting a newly released model.
* **Plausible Counterexamples:** Optimal routing policies are harness-invariant and transfer across $H_{\text{minimal}}$ and $H_{\text{full}}$ with zero ranking reversals.
* **Falsification Condition:** H8 is falsified if the router-by-harness interaction term $\sigma^2_{RH}$ is statistically indistinguishable from zero ($p > 0.10$) and zero policy ranking reversals occur across harnesses, or if model-ID-bound routers show no degradation under candidate model substitution.


## 7. Experimental Design and Baseline Definitions

To prevent methodological circularity—where a router appears superior solely because it accesses a stronger model catalog, benefits from hidden prompt optimization, or runs inside a more forgiving harness—the experimental design enforces strict **ceteris paribus controls** across a multi-dimensional factorial structure.

### 7.2 Task Taxonomy, Complexity Stratification, and Contamination Controls
To ensure external validity across realistic software engineering workloads while guarding against benchmark memorization ([Does SWE-Bench-Verified Test Agent Ability or Model Memory?, arXiv:2512.10218](https://arxiv.org/abs/2512.10218)), the task corpus is constructed as a **stratified, multi-source benchmark suite** spanning four complexity strata (S1–S4) and three provenance tracks:

1. **Provenance Track 1 — Standardized Public Anchor (`Corpus-Public`):** Stratified sample from [SWE-bench Verified](https://www.swebench.com/verified.html) (disjoint from the 40-instance static training split of [TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)) and [SWE-Bench Pro (arXiv:2509.16941)](https://arxiv.org/pdf/2509.16941) / [SWE-Bench ProMax (arXiv:2608.09802)](https://arxiv.org/abs/2608.09802) (multilingual Python, TypeScript, Go, and Rust tasks).
2. **Provenance Track 2 — Mutation-Hardened Anti-Contamination Split (`Corpus-Mutated`):** Applying the benchmark mutation methodology of [Saving SWE-Bench (arXiv:2510.08996)](https://arxiv.org/abs/2510.08996), identifier names, error strings, AST structures, and line offsets in a paired subset of `Corpus-Public` are semantically mutated while preserving exact functional equivalence and test oracle semantics. Comparing router and model performance between `Corpus-Public` and `Corpus-Mutated` directly measures memorization leakage.
3. **Provenance Track 3 — Post-Cutoff Live Repository Split (`Corpus-Live`):** Newly resolved GitHub pull requests with executable `FAIL_TO_PASS` and `PASS_TO_PASS` test suites harvested from active open-source repositories stamped **strictly after the latest training knowledge cutoff** of all candidate models in $\mathcal{M}$.

Tasks within each provenance track are stratified across a $4 \times 3$ **Complexity-by-Task-Type Matrix**:
* **Task Types:** (T1) Bug Diagnosis & Fault Repair, (T2) Feature Implementation & API Extension, (T3) Multi-File Refactoring, Performance Optimization & Test Authoring.
* **Complexity Strata (anchored to human resolution time, patch scope, and static `CodeHealth` per [Triage, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)):**
  * **Stratum S1 (Trivial / Localized):** Single-file edit, $\le 15$ lines changed, human fix time $<15$ minutes, `CodeHealth` $\ge 9$, zero new dependencies.
  * **Stratum S2 (Standard / Module-Scoped):** 1–3 files edited, 15–60 lines changed, human fix time 15–60 minutes, `CodeHealth` 6–8, localized unit test failures.
  * **Stratum S3 (Complex / Cross-Module):** 3–8 files edited, 60–200 lines changed, human fix time 1–4 hours, `CodeHealth` 3–6, subtle state/concurrency/type interactions.
  * **Stratum S4 (Architectural / Deep Legacy):** $>8$ files or $>200$ lines changed, human fix time $>4$ hours, `CodeHealth` $<3$, requiring multi-stage design, migration, and regression containment.

### 7.3 Locked Model Roster, Effort Controls, and Harness Parity
To eliminate the confounder where a router wins merely because it can access a superior model or a different reasoning-effort setting, all policies (except the isolated `Track P7-Open` sensitivity arm) operate over a **strictly locked 4-tier model pool $\mathcal{M}$ and discrete effort space $\mathcal{E} = \{\texttt{low}, \texttt{medium}, \texttt{high}\}$**:

1. **Model Roster Parity:** Following the tier-pool design of [TwinRouterBench (arXiv:2605.18859)](https://arxiv.org/html/2605.18859v1), the locked pool $\mathcal{M}$ comprises four capability-and-price tiers (`Tier 0: Low / Economical`, `Tier 1: Mid`, `Tier 2: Mid-High`, `Tier 3: High / Frontier`), with pinned, dated model version snapshots (never floating `-latest` aliases) and identical decoding parameters ($\text{temperature} = 0.2$, $\text{top\_p} = 1.0$, max output tokens $= 16,384$).
2. **Effort-Level Parity:** Because modern models expose inference-time compute scaling (`reasoning_effort` or thinking budgets) and routers like [OpenRouter Auto Code](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/) and [TypeSafe Jev Router](https://openrouter.ai/typesafe/jev-router) jointly select $(m, e)$, every model $m \in \mathcal{M}$ that supports effort modulation is exposed as discrete routable $(m, e)$ arms to all candidate policies, including fixed baselines and human selectors.
3. **Harness Disclosure and Factorial Control (ETCSOVG Standard):** Adopting the framework of [Zhang et al. (2026, arXiv:2605.23950)](https://arxiv.org/html/2605.23950v1), all policies execute inside a locked container environment with a published **ETCSOVG Harness Card** (Execution, Tool, Context, Scheduling, Observability, Verification, Governance). To test RQ8 (harness-router coupling), the confirmatory experiment runs the primary evaluation under a standardized production-grade closed-loop harness ($H_{\text{std}}$, e.g., `mini-swe-agent` v2.2.8 / OpenHands with 50-step cap and 120s per-step timeout) and replicates a stratified subset across $H_{\text{minimal}}$ (append-only context, raw tool errors, no self-check) and $H_{\text{full}}$ (compressed BM25 retrieval context, minimal tool schema, structured error feedback, and anomaly rollback per [arXiv:2605.23950 Table 8](https://arxiv.org/html/2605.23950v1)).
4. **Prompt Semantics Control:** Because minor prompt wording differences alter deliberative token expenditure and tool behavior ([Prompt-Induced Waste in Coding Agents, arXiv:2608.01347](https://arxiv.org/abs/2608.01347)), the system prompt, tool definitions, and user instruction template are byte-identical across all routing policies. As warned by [DeepInspect (2026)](https://www.deepinspect.ai/blog/notdiamond-alternatives), any router feature that rewrites or optimizes the user/system prompt (such as Not Diamond's prompt optimization module) is hard-disabled during routing experiments.

### 7.4 Pilot vs. Confirmatory Split, Counterbalancing, and Human Baseline Protocol
* **Strict Three-Way Corpus Partition:** The task corpus $\mathcal{D}$ is partitioned into three strictly disjoint subsets stratified by repository, task type, and complexity stratum:
  1. $\mathcal{D}_{\text{train/cal}}$ (**Training & Threshold Calibration Split**): Used exclusively to train supervised routers (`P6`), fit Platt/isotonic probability calibration, tune `TypeSafe Jev` confidence bands (`P5`), set `Triage` heuristic cutoffs (`P4`), and estimate variance components for power calculations.
  2. $\mathcal{D}_{\text{pilot}}$ (**Pilot Go/No-Go Split**): Used to verify harness stability, audit step-level labels, and test pilot feasibility gates ([Triage §4, arXiv:2604.07494](https://arxiv.org/html/2604.07494v1)) before locking the preregistered analysis plan.
  3. $\mathcal{D}_{\text{confirm}}$ (**Confirmatory Held-Out Evaluation Split**): Locked in an encrypted/hash-pinned manifest prior to confirmatory execution; zero hyperparameter tuning, threshold adjustment, or prompt modification is permitted on $\mathcal{D}_{\text{confirm}}$.
* **Randomization, Matching, and Counterbalancing:** All automated policies (`P2`–`P8`) are evaluated in a **fully crossed within-task paired design** (every policy runs on every task $j \in \mathcal{D}_{\text{confirm}}$ across $K \ge 3$ independent trials with distinct random seeds/timestamps to capture provider latency and generation stochasticity). To prevent time-of-day provider load, rate-limiting, or transient outage bias, policy execution order for each task $j$ and trial $k$ is randomized via a **Williams Latin Square** design, executing interleaved calls within the same 15-minute window.
* **Human Baseline Recruitment and Counterbalancing (`P1_Human`):** Qualified software engineers are recruited across three verified expertise strata: **Junior** (1–3 years professional SE experience), **Mid-Level** (3–6 years), and **Senior/Staff** ($\ge 6$ years + open-source maintainer history). Participants receive a standardized model-catalog dossier detailing each candidate model's pricing (input, cache read/write, output), context window, speed, and general capability profile (identical to the metadata provided to automated routers). Tasks are assigned to human raters via a **Balanced Incomplete Block Design (BIBD)** with Williams crossover ordering across information conditions (`P1a_HumanIssueOnly` vs. `P1b_HumanRepoAware`) so that every task is independently routed by at least 3 engineers (one per expertise tier) without rater fatigue or task-memory carryover.

### 7.5 Blind Independent Verification and Failure/Timeout Handling
1. **Three-Tier Blind Independent Verification:** Because a weak repository test suite can pass a defective or overfitted patch ("pseudo-pass"), task success $Y_{j,k} \in \{0,1\}$ is determined by an independent verification pipeline completely blinded to which routing policy or model produced the patch:
   * *Gate V1 (Official Harness Test Predicate):* Execution of the repository's `FAIL_TO_PASS` and `PASS_TO_PASS` test suites in a clean container.
   * *Gate V2 (Augmented Mutation & Regression Suite):* Execution of augmented edge-case and regression tests following [UTBoost (arXiv:2506.09289)](https://casrai.org/guides/swe-bench) and [SWE-Bench+ (arXiv:2410.06992)](https://arxiv.org/abs/2410.06992) to catch patches that pass weak original tests via test deletion, hardcoding, or narrow workarounds.
   * *Gate V3 (Double-Blind Human Code Review Audit):* On a stratified 20% random sample of Gate V2 passes, two independent senior reviewers—blinded to the policy, model, and cost—grade the diff on a structured rubric (architectural soundness, security/injection safety, maintainability, and absence of unintended side effects).
2. **Failure, Retry, Escalation, and Timeout Handling:** Every run is subject to a hard step budget ($N_{\text{max}} = 50$ steps) and wall-clock timeout ($T_{\text{max}} = 30$ minutes per task, $120$ seconds per step). Transient infrastructure errors (HTTP 429 rate limits, 502/503 gateway errors, container daemon crashes) are retried up to 3 times with exponential backoff and logged separately from model/routing failures; persistent infrastructure failures are flagged for sensitivity analysis, whereas malformed tool calls, context-window overflows, step-budget exhaustion, and test failures are recorded as **genuine trajectory failures ($Y_{j,k} = 0$)** with all consumed tokens billed in full.


## 8. Measurement Instruments and Economic Framework

A rigorous economic methodology must price every resource consumed along the trajectory—including the router's own decision overhead, prompt-cache invalidation penalties, tool sandboxes, retries, and failed attempts.

### 8.1 Micro-Economic Cost Accounting per Trajectory Step
Consider an agent trajectory $\tau_j = (s_{j,1}, s_{j,2}, \dots, s_{j,N_j})$ on task instance $j$. At each step $i \in \{1, \dots, N_j\}$, the routing policy $\pi$ observes state $x_{j,i}$ and selects a model $m_{j,i} \in \mathcal{M}$ and reasoning effort $e_{j,i} \in \mathcal{E}$.

#### 1. Four-Bucket Generation Token Cost ($C^{\text{gen}}_{j,i}$)
Following the four-bucket billing architecture of modern API providers and [TwinRouterBench (arXiv:2605.18859)](https://arxiv.org/html/2605.18859v1), prompt tokens at step $i$ are partitioned into fresh un-cached input tokens ($n^{\text{in}}_{j,i}$), cached prefix read tokens ($n^{\text{cr}}_{j,i}$), and cache-write tokens ($n^{\text{cw}}_{j,i}$), while generated tokens are partitioned into visible completion tokens ($n^{\text{out}}_{j,i}$) and internal deliberative/thinking tokens ($n^{\text{think}}_{j,i}$):

$$C^{\text{gen}}_{j,i}(m_{j,i}, e_{j,i}) = \frac{n^{\text{in}}_{j,i} p^{\text{in}}_{m_{j,i}} + n^{\text{cr}}_{j,i} p^{\text{cr}}_{m_{j,i}} + n^{\text{cw}}_{j,i} p^{\text{cw}}_{m_{j,i}} + \left(n^{\text{out}}_{j,i} + n^{\text{think}}_{j,i}\right) p^{\text{out}}_{m_{j,i}}}{10^6}$$

Crucially, if step $i$ switches models ($m_{j,i} \neq m_{j,i-1}$) or if the elapsed time since the last call to $m_{j,i}$ exceeds the provider's cache time-to-live ($\text{TTL}$, typically 300 seconds), the entire prefix at step $i$ incurs a cold cache rebuild ($n^{\text{cw}}_{j,i} = |M_{j,i}|$, $n^{\text{cr}}_{j,i} = 0$) at the incoming model's `cache_write` rate $p^{\text{cw}}_{m_{j,i}}$ ([TwinRouterBench §5.1, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1); [OpenRouter Auto Code Announcement](https://openrouter.ai/blog/announcements/auto-and-auto-code-routers/)).

#### 2. Routing and Orchestration Decision Cost ($C^{\text{route}}_{j,i}$)
The direct cost of executing the routing decision at step $i$ includes any classifier, embedding, prefill encoder, or LLM-judge tokens plus hosted router fees:

$$C^{\text{route}}_{j,i}(\pi) = \frac{n^{\text{r-in}}_{j,i} p^{\text{r-in}}_{\pi} + n^{\text{r-cr}}_{j,i} p^{\text{r-cr}}_{\pi} + n^{\text{r-out}}_{j,i} p^{\text{r-out}}_{\pi}}{10^6} + t^{\text{r-cpu/gpu}}_{j,i} \cdot r_{\text{compute}} + f^{\text{gateway}}_{j,i}$$

For example, under `P5a_JevZeroShot` ([TypeSafe Jev 1.14](https://openrouter.ai/typesafe/jev-1.14)), $p^{\text{r-in}}_{\pi} = \$0.042/\text{1M}$ and $p^{\text{r-out}}_{\pi} = \$0$; under `P8b_SwitchyardEscalation` ([LangChain Switchyard Benchmark](https://www.langchain.com/blog/switchyard-agent-routing-benchmark)), $C^{\text{route}}_{j,i}$ captures the full un-cached judge model invocation on every weak-tier turn; under `P8c_PrefillMLP` ([Varshney et al., arXiv:2603.20895](https://arxiv.org/html/2603.20895v2)), $C^{\text{route}}_{j,i}$ prices the GPU compute of running prefill through the open-weight encoder.

#### 3. Tool Execution, Sandbox Infrastructure, and Verification Cost ($C^{\text{infra}}_{j}$)
Containerized code execution, test runner compute, and automated verification gates consume active compute time $T^{\text{sandbox}}_j$ (seconds), priced at cloud container rates $r_{\text{sandbox}}$ (e.g., OpenRouter's hosted shell rate of $\$0.0001/\text{active second}$ or AWS Fargate/Modal vCPU-second rates):

$$C^{\text{infra}}_j = \left(\sum_{i=1}^{N_j} t^{\text{tool}}_{j,i} + t^{\text{verify}}_j\right) \cdot r_{\text{sandbox}}$$

#### 4. Total Realized Trajectory Cost ($C_j(\pi)$)
Summing over all initial attempts, internal retries, and verification-gate fallback executions on task $j$ yields the realized trajectory expenditure:

$$C_j(\pi) = \sum_{a=1}^{A_j} \sum_{i=1}^{N_{j,a}} \left[ C^{\text{gen}}_{j,a,i} + C^{\text{route}}_{j,a,i} \right] + C^{\text{infra}}_j + \mathbb{I}(\pi = \text{P1\_Human}) \cdot w_{\text{eng}} \cdot t^{\text{human}}_j$$

where $A_j$ is the number of attempts/escalations within the policy's allowed budget and $w_{\text{eng}} \cdot t^{\text{human}}_j$ is reported both **excluded** (Pure API Cost View) and **included** (Fully Loaded Engineering View).

### 8.2 Subscription Quotas vs. Marginal API Billing
Because software engineering teams deploy coding agents under two distinct commercial regimes—(1) **Pay-Per-Token API Billing** and (2) **Fixed-Price Rate-Limited Subscriptions / Enterprise Reserved Capacity** (e.g., $\$20\text{--}\$200/\text{month}$ seat plans with rolling 5-hour or weekly message/token caps, or provisioned GPU throughput)—the methodology models both:

* **Regime 1 (Marginal API Billing):** Every token is priced at its live provider list rate (plus gateway fee, if any).
* **Regime 2 (Quota-Depletion & Opportunity-Cost Accounting):** Under a subscription plan with fixed periodic cost $B_{\text{sub}}$ and rolling quota capacity $Q_{\text{cap}}$ (measured in frontier-equivalent compute units per window $W$), consuming $q_{j,i}$ quota units on a routine step carries a **shadow price** $\lambda_{\text{quota}}$ equal to the expected overflow API cost or developer blocking cost when the quota saturates before the window resets:
  $$C^{\text{sub}}_{j}(\pi) = \frac{B_{\text{sub}}}{Q_{\text{cap}}} \sum_{i=1}^{N_j} q_{j,i} + \mathbb{P}\left(\sum_{\text{window } W} Q > Q_{\text{cap}}\right) \cdot \left(C^{\text{API-overflow}}_j + w_{\text{eng}} \cdot T_{\text{throttled}}\right)$$
  This formulation tests whether routing's primary value in subscription environments is **quota preservation** (preventing developer lock-out during peak debugging sprints) rather than direct per-token invoice reduction.

### 8.3 Primary Outcome Metrics and Elimination of Survivorship Bias
Calculating average cost exclusively over resolved tasks ($Y_j = 1$) introduces severe **survivorship bias**: a router that routes 95% of tasks to a cheap model that fails quickly for $\$0.02$ and resolves only 5% of easy tasks for $\$0.01$ would appear to have a $\$0.01$ "cost per solved task," masking the 95% failure rate ([TwinRouterBench Appendix A.15, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)). To eliminate survivorship bias, this methodology defines two primary failure-inclusive economic outcomes alongside disaggregated secondary metrics:

1. **Primary Outcome 1 — Total Economic Cost per Independently Verified Successful Completion ($\text{TEC}_{\text{succ}}$):**
   $$\text{TEC}_{\text{succ}}(\pi) = \frac{\sum_{j=1}^{M} C_j(\pi)}{\sum_{j=1}^{M} Y_j(\pi)} = \frac{\bar{C}(\pi)}{\hat{P}_{\text{succ}}(\pi)}$$
   Here, the numerator sums the full economic cost across **all $M$ attempted tasks** (both resolved $Y_j=1$ and unresolved/abandoned $Y_j=0$), while the denominator counts only tasks that pass blind independent verification (Gate V2). Every dollar burned on failed attempts, infinite loops, and aborted trajectories directly inflates $\text{TEC}_{\text{succ}}(\pi)$.
2. **Primary Outcome 2 — Remediation-Penalized Per-Instance Bill ($\text{Bill}_j(\pi)$):**
   Adapting and extending the dynamic leaderboard bill of [TwinRouterBench (§5.2, arXiv:2605.18859)](https://arxiv.org/html/2605.18859v1), each task instance $j$ is assigned a remediation-penalized cost:
   $$\text{Bill}_j(\pi) = C_j(\pi) + \left(1 - Y_j(\pi)\right) \cdot \gamma_{\text{rem}} + \mathbb{I}\left(\text{SilentRegression}_j(\pi) = 1\right) \cdot \gamma_{\text{reg}}$$
   where $\gamma_{\text{rem}}$ is the remediation penalty for an unresolved task (swept in sensitivity analysis from the perfect-solver API fallback price $\gamma_{\text{rem}} = \$0.60$ used in [TwinRouterBench](https://arxiv.org/html/2605.18859v1) up to human developer remediation cost $\gamma_{\text{rem}} = w_{\text{eng}} \cdot T_{\text{manual},j}$), and $\gamma_{\text{reg}} \ge \gamma_{\text{rem}}$ is the additional penalty when a policy submits a silent regression that passes weak harness checks (Gate V1) but fails independent verification (Gate V2/V3).
3. **Required Disaggregated Secondary Metrics:** To prevent single-number gaming, every experimental report must publish the joint distribution (mean, standard deviation, median, IQR, p90, and p99) of: (a) Verified Resolution Rate $\hat{P}_{\text{succ}}$; (b) Raw Trajectory Cost $C_j$ stratified by resolved ($Y_j=1$) vs. failed ($Y_j=0$) runs; (c) Silent Regression Rate ($\text{SRR}$); (d) End-to-End Wall-Clock Latency ($T_{\text{wall},j}$) and Routing Overhead Latency ($T_{\text{route},j}$); (e) Cache Hit Ratio ($\text{CHR}_j$) and Switch Count ($N_{\text{switch},j}$); and (f) Failure-Aware Cost Savings (`CostSave` Variant E from [TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)).

### 8.4 Economic Break-Even Formulations and Sensitivity Analyses
Beyond point estimates under a single day's price sheet, the economic framework conducts four formal sensitivity sweeps:
1. **Inter-Tier Price Compression Sweep:** Simulating provider price drops on frontier models versus economical models across price ratios $\kappa \in \{1.5, 2, 5, 10, 25, 50, 100\}$ by re-pricing recorded token buckets $(n^{\text{in}}, n^{\text{cr}}, n^{\text{cw}}, n^{\text{out}})$ to identify the exact price-ratio frontier where each router ceases to be cost-effective.
2. **Prompt-Cache Discount & TTL Sensitivity:** Sweeping `cache_read` discounts from $0\%$ (no caching) to $95\%$ and `cache_write` surcharges from $1.0\times$ to $2.0\times$ to quantify how much cache-aware policies (`P8a_SwitchyardStage`, `P7b_OpenRouterAutoCode`) gain from cache locality.
3. **Amortization of Router Training and Labeling Costs ($N_{\text{break-even}}$):** For supervised routers (`P6_LearnedRouter`) that incur an upfront offline dataset construction and training cost $C_{\text{offline}}$ (e.g., $\$2,771.84$ + 1,000 GPU-hours in [LLMRouterBench, arXiv:2601.07206](https://arxiv.org/html/2601.07206v1), or sequential downgrade probing in [TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)), computing the minimum production task volume required to amortize training before model catalog drift forces re-labeling:
   $$N_{\text{break-even}} = \frac{C_{\text{offline}}}{\mathbb{E}[\text{Bill}(\text{ZeroShotBaseline})] - \mathbb{E}[\text{Bill}(\text{LearnedRouter})]}$$
4. **Remediation Penalty ($\gamma_{\text{rem}}$) Willingness-to-Pay Sweep:** Sweeping $\gamma_{\text{rem}} \in [\$0.50, \$500.00]$ to map optimal policy selection from autonomous batch background sweeps (low $\gamma_{\text{rem}}$) to interactive senior-engineer pairing or mission-critical production hotfixes (high $\gamma_{\text{rem}}$).


## 9. Statistical Analysis Plan

Software engineering agent trajectories violate classical parametric assumptions: resolution outcomes $Y_{j,k} \in \{0,1\}$ are correlated binary variables nested within tasks and repositories, while costs $C_{j,k}$ and latencies $T_{j,k}$ are strictly positive, zero-inflated (for router overhead), and heavily right-skewed due to rare retry spirals ([LangChain Switchyard Benchmark, 2026](https://www.langchain.com/blog/switchyard-agent-routing-benchmark); [Kitchenham & Madeyski, 2024](https://www.researchgate.net/publication/383204756_Recommendations_for_analysing_and_meta-analysing_small_sample_size_software_engineering_experiments)).

### 9.1 Paired Comparisons and Hierarchical Mixed-Effects Models
1. **Binary Resolution Outcomes ($Y_{j,k}$):**
   * *Omnibus & Pairwise Non-Parametric Tests:* Cochran's $Q$ test across all $P$ policies on trial-aggregated task resolution, followed by exact McNemar's test with mid-$p$ confidence intervals for paired policy comparisons ([Fay & Lumbard, 2021](https://bufnets.tech/index.php/bufnets/article/view/188)).
   * *Hierarchical Generalized Linear Mixed Model (Binomial GLMM):* To account for repeated trials $k \in \{1 \dots K\}$, task-level difficulty random effects, and repository-level clustering $r(j)$, resolution probability is modeled via a logistic GLMM:
     $$\text{logit}\left(\mathbb{P}(Y_{j,k,p} = 1)\right) = \beta_0 + \beta_p \cdot \text{Policy}_p + \gamma_s \cdot \text{Stratum}_{s(j)} + (\beta \gamma)_{p,s} + u_{\text{repo}(j)} + v_{\text{task}(j)}$$
     where $u_{\text{repo}} \sim \mathcal{N}(0, \sigma^2_{\text{repo}})$ and $v_{\text{task}} \sim \mathcal{N}(0, \sigma^2_{\text{task}})$ capture nested hierarchical variance.
2. **Right-Skewed Cost and Tail-Risk Outcomes ($C_{j,k}$ and $\text{Bill}_{j,k}$):**
   * *Non-Parametric Superiority Estimators:* Following [Kitchenham & Madeyski (2024)](https://www.researchgate.net/publication/383204756_Recommendations_for_analysing_and_meta-analysing_small_sample_size_software_engineering_experiments) and [Triage (arXiv:2604.07494)](https://arxiv.org/html/2604.07494v1), pairwise cost comparisons report the **paired Brunner-Munzel test** and the **Probability of Superiority** effect size $\hat{p}_{A,B} = \mathbb{P}(C_A < C_B) + 0.5 \mathbb{P}(C_A = C_B)$, which requires no normality or homoscedasticity assumptions and is resilient to extreme cost outliers.
   * *Two-Part Hurdle / Gamma-Log GLMM:* Trajectory costs are modeled via a Gamma GLMM with a log link ($\log(\mathbb{E}[C_{j,k,p}]) = \mathbf{X}_{j,p}\boldsymbol{\theta} + u_{\text{repo}(j)} + v_{\text{task}(j)}$), supplemented by **Quantile Regression** at the 50th, 90th, and 99th percentiles to explicitly test tail-cost inflation from rare, expensive escalation spirals.
3. **Uncertainty Intervals for Ratio Metrics ($\text{TEC}_{\text{succ}}$):**
   Because $\text{TEC}_{\text{succ}}(\pi) = \bar{C}(\pi) / \hat{P}_{\text{succ}}(\pi)$ is a ratio of two correlated random variables, standard Gaussian error propagation is invalid near small denominators. Confidence intervals ($95\%$ and $99\%$) for $\text{TEC}_{\text{succ}}(\pi)$ and pairwise differences $\Delta \text{TEC}_{\text{succ}}(\pi_A, \pi_B)$ are constructed via a **Two-Stage Hierarchical Bias-Corrected and Accelerated (BCa) Cluster Bootstrap** ($B = 10,000$ resamples, resampling repositories at Level 1 and tasks within repositories at Level 2, preserving the paired structure across policies).

### 9.2 Multiple-Comparison Corrections and Practical Equivalence Testing
With 8 candidate policy families (28 all-pairs comparisons), unadjusted $p$-values guarantee family-wise Type I error inflation. The analysis plan enforces a two-tier multiplicity protocol:
1. **Confirmatory Primary Hypotheses (H1–H8):** Pre-specified focal contrasts (e.g., each router vs. `P2a_FixedEcon`, `P2c_FixedFrontier`, and `P1b_HumanRepoAware`) are controlled for Family-Wise Error Rate (FWER) at $\alpha = 0.05$ using the **Holm-Bonferroni step-down procedure**.
2. **Exploratory All-Pairs & Subgroup Contrasts:** Controlled for False Discovery Rate (FDR) at $q = 0.05$ using the **[Benjamini-Hochberg (1995)](https://academic.oup.com/jrsssb/article/57/1/289/7035855)** procedure.
3. **Equivalence and Non-Inferiority Testing (TOST):** To distinguish a genuine null result ("Router A and Fixed Baseline B perform equivalently") from an underpowered inconclusive test, small differences are analyzed via **Two One-Sided Tests (TOST)** against pre-specified Equivalence Bounds: $\pm \delta_P = \pm 3.0$ percentage points for resolution rate and $\pm \delta_C = \pm 10\%$ for $\text{TEC}_{\text{succ}}$.

### 9.3 Pareto Cost-Effectiveness Frontiers, ICER, and Net Monetary Benefit
To synthesize the multi-objective trade-off between accuracy, cost, and latency, the analysis constructs four complementary econometric surfaces:
1. **Empirical Pareto Frontier & Pareto Distance (`ParetoDist`):** Following [LLMRouterBench (§3.4, arXiv:2601.07206)](https://arxiv.org/html/2601.07206v1), policy $\pi_1$ Pareto-dominates $\pi_2$ if $\hat{P}_{\text{succ}}(\pi_1) \ge \hat{P}_{\text{succ}}(\pi_2)$ and $\bar{C}(\pi_1) \le \bar{C}(\pi_2)$ with at least one strict inequality. Each policy's `ParetoDist` ($\ell_1$ distance to the empirical frontier in normalized space) and **Model Delta Padded Area Under the Cost-Coverage Curve (`MDP-AUCCC`)** ([Varshney et al., arXiv:2603.20895](https://arxiv.org/html/2603.20895v2)) are reported with bootstrap confidence bands.
2. **Incremental Cost-Effectiveness Ratio (ICER) & Cost-Effectiveness Acceptability Curves (CEAC):** Borrowing from health-economic decision theory, for any non-dominated policy $\pi_k$ ordered by increasing cost relative to the next cheapest non-dominated policy $\pi_{k-1}$:
   $$\text{ICER}(\pi_k, \pi_{k-1}) = \frac{\bar{C}(\pi_k) - \bar{C}(\pi_{k-1})}{\hat{P}_{\text{succ}}(\pi_k) - \hat{P}_{\text{succ}}(\pi_{k-1})}$$
   which measures the marginal dollar cost per additional resolved software engineering issue. For a decision-maker's willingness-to-pay threshold $\lambda_{\text{WTP}}$ per resolved issue, the **Net Monetary Benefit (NMB)** is $\text{NMB}_j(\pi; \lambda_{\text{WTP}}) = \lambda_{\text{WTP}} \cdot Y_j(\pi) - C_j(\pi)$. Sweeping $\lambda_{\text{WTP}} \in [\$0.10, \$500.00]$ across the 10,000 bootstrap replicates generates the **Cost-Effectiveness Acceptability Curve (CEAC)**, plotting the exact probability that each policy $\pi$ maximizes net economic benefit at any organizational budget posture.

### 9.4 Analyzing Specific Methodological Challenges
* **Rare but Expensive Failures:** Evaluated via Expected Shortfall / Conditional Value-at-Risk ($\text{CVaR}_{0.95}$ and $\text{CVaR}_{0.99}$ of trajectory cost $C_j$), isolating the mean cost of the worst 5% and 1% of runaway trajectories.
* **Variation Between Repositories:** Quantified via the Intraclass Correlation Coefficient ($\text{ICC}_{\text{repo}} = \sigma^2_{\text{repo}} / (\sigma^2_{\text{repo}} + \sigma^2_{\text{task}} + \sigma^2_{\epsilon})$) and leave-one-repository-out cross-validation (LORO-CV).
* **Human-Selection Variance (`P1_Human`):** Analyzed via Fleiss' $\kappa$ and Krippendorff's $\alpha$ (ordinal, across model tiers) among raters, plus a random-effects rater term $u_{\text{rater}} \sim \mathcal{N}(0, \sigma^2_{\text{rater}})$ in the GLMM to separate systematic human intuition from individual rater noise.

### 9.5 Prospective Power Analysis and Sequential Stopping Rules
No sample sizes or significance levels are fabricated a priori. Instead, sample size $M$ (number of tasks) and $K$ (repeats per task) for the confirmatory phase are determined prospectively from the variance parameters estimated in the Phase 2 Pilot ($\hat{p}_{\text{discordant}}$, $\hat{\sigma}^2_{\text{repo}}$, $\hat{\sigma}^2_{\text{task}}$, $\hat{\sigma}^2_{\text{trial}}$):
* **Paired Binary Resolution Power (McNemar):** To detect a minimum practically significant difference of $\Delta P = 0.05$ with power $1-\beta = 0.80$ at two-sided Holm-adjusted $\alpha_{\text{adj}}$ given pilot discordant pair proportion $\psi = p_{10} + p_{01}$, the required number of independent tasks is:
  $$M_{\text{binary}} = \left\lceil \frac{\left(z_{1-\alpha_{\text{adj}}/2}\sqrt{\psi} + z_{1-\beta}\sqrt{\psi - (\Delta P)^2}\right)^2}{(\Delta P)^2} \right\rceil \cdot \text{DEFF}_{\text{repo}}$$
  where $\text{DEFF}_{\text{repo}} = 1 + (\bar{m}_{\text{repo}} - 1)\text{ICC}_{\text{repo}}$ adjusts for within-repository clustering.
* **Simulation-Based GLMM Power & Group-Sequential Stopping Rule:** Because cost ratios ($\text{TEC}_{\text{succ}}$) follow non-normal hierarchical distributions, prospective power is verified via 5,000 Monte Carlo simulations parameterized by pilot residuals. To prevent wasteful API expenditure if a policy catastrophically fails or if bounds are met early, confirmatory execution employs an **O'Brien-Fleming group-sequential alpha-spending design** with two pre-planned interim looks (at $50\%$ and $75\%$ of tasks) and a **harm/futility stopping rule**: any routing policy whose interim verified resolution rate falls $>15$ percentage points below `P2c_FixedFrontier` at $p < 0.001$ (or whose conditional power to beat the cheaper fixed baseline is $<10\%$) is halted early for futility, with all interim data retained and reported.


## 10. Threats to Validity and Mitigations

Following the four-category validity taxonomy of [Shadish, Cook, & Campbell (2002)](https://portal.research.lu.se/en/publications/experimentation-in-software-engineering-2024-edition/) and [Wohlin et al. (2012/2024, *Experimentation in Software Engineering*)](https://portal.research.lu.se/en/publications/experimentation-in-software-engineering-2024-edition/), Table 10.1 maps ten domain-specific confounders to concrete experimental mitigations.

| Validity Category | Specific Confounder / Threat | Mechanism of Distortion | Methodological Mitigation in This Protocol |
| :--- | :--- | :--- | :--- |
| **Construct Validity** | **1. Survivorship-Biased Cost Metrics** | Computing average cost only over solved tasks rewards routers that fail cheaply on hard tasks ([TwinRouterBench App. A.15, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)). | Define primary outcome as $\text{TEC}_{\text{succ}} = \sum_{\text{all}} C_j / \sum Y_j$ and remediation-penalized $\text{Bill}_j = C_j + (1-Y_j)\gamma_{\text{rem}}$. |
| **Construct Validity** | **2. Verification Quality & Pseudo-Passes** | Weak repository unit tests allow broken or overfitted patches from cheap models to count as successes ([SWE-Bench+, arXiv:2410.06992](https://arxiv.org/abs/2410.06992)). | Enforce 3-tier verification: official test suite (V1) + [UTBoost](https://casrai.org/guides/swe-bench) augmented mutation tests (V2) + blinded human review audit (V3). |
| **Construct Validity** | **3. Subscription vs. API Economic Mismatch** | API list prices do not reflect rate-limited flat subscriptions or self-hosted GPU economics ([LangChain Switchyard, 2026](https://www.langchain.com/blog/switchyard-agent-routing-benchmark)). | Report dual accounting (Marginal API View + Subscription Quota Shadow-Price View) and run inter-tier price sensitivity sweeps. |
| **Internal Validity** | **4. Model Capability & Catalog Asymmetry** | Commercial routers (`openrouter/auto-code`) access 600+ models while binary routers access 2 ([LLMRouterBench, arXiv:2601.07206](https://arxiv.org/html/2601.07206v1)). | Lock all routers (`P1`–`P8`, including `Track P7-Locked` via `allowed_models`) to the identical 4-tier model pool $\mathcal{M}$ and effort set $\mathcal{E}$. |

| **Internal Validity** | **7. Prompt Caching & Switching Hysteresis** | Ignoring `cache_read` vs. `cache_write` overstates step-level routing savings or distorts cold-start costs ([TwinRouterBench, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1)). | Meter realized provider `cache_read` and `cache_write` buckets per turn and enforce clean-room cache isolation between independent task runs. |
| **Internal Validity** | **8. Provider Reliability & Time-of-Day Drift** | API latency, throttling, and silent quantization shifts vary across hours and days. | Execute all policies on task $j$ via Williams Latin Square interleaving within the same 15-minute window; pin exact dated provider snapshots. |
| **External Validity** | **9. Benchmark Leakage & Task Familiarity** | Pre-cutoff SWE-bench Verified issues may be memorized in frontier weights ([arXiv:2512.10218](https://arxiv.org/abs/2512.10218)), inflating frontier accuracy or router confidence. | Evaluate across three provenance splits: `Corpus-Public`, `Corpus-Mutated` ([arXiv:2510.08996](https://arxiv.org/abs/2510.08996)), and post-cutoff `Corpus-Live` across 4 languages. |
| **Statistical-Conclusion Validity** | **10. Human Expertise Variance & Underpowered Nulls** | Developer skill variance in `P1_Human` or heavy-tailed cost outliers mask true differences or inflate false positives. | Stratify human raters across Junior/Mid/Senior tiers using a BIBD crossover design; use Brunner-Munzel $\hat{p}$, BCa cluster bootstrap, Holm/BH corrections, and TOST equivalence bounds. |

| :--- | :--- | :--- | :--- |

### Why Negative or Null Results Are Highly Publishable Under This Design
Because the experimental design incorporates **TOST equivalence testing**, **prospective power verification**, **locked harness/pool parity**, and **three-tier blind verification**, a negative result—such as proving that (a) `openrouter/auto-code` or learned routers do not outperform a single mid-high model (`P2b_FixedMid`) or a 10-line deterministic `CodeHealth` rule (`P4b_TriageCodeHealth`) once cache invalidation and failed trajectories are priced, or (b) improving the execution harness ($H_1 \to H_3$) yields $5\times$ larger economic savings than deploying any model router—directly refutes prevailing industry assumptions and provides actionable engineering guidance for the AI systems community.


## 14. Open Questions Requiring Further Investigation

Even with the controls specified above, six foundational questions lie at the boundary of current measurement science and warrant dedicated follow-up investigation:

1. **Counterfactual Prefix Divergence in Multi-Turn Trajectories:** In live dynamic execution, once Router A chooses model $m_1$ at step $i$ and Router B chooses $m_2$, their repository states and message prefixes $M_{i+1}$ diverge for all subsequent steps $i+1 \dots N$. How can researchers disentangle the **immediate single-step quality** of a routing decision at step $i$ from the **stochastic downstream compounding** of later steps without incurring $O(|\mathcal{M}|^N)$ branching tree executions ([TwinRouterBench §1, arXiv:2605.18859](https://arxiv.org/html/2605.18859v1))?
2. **Interaction Between Context Compaction and Stateful Routers:** Long-horizon coding agents periodically compact or summarize their conversation history when approaching context-window limits ([LiteLLM Switchyard Blog, Nov 6, 2026](https://docs.litellm.ai/blog/switchyard-tool-aware-routing)). When a harness compacts context, how do embedding-based routers (`P6`), prefill-activation routers (`P8c`), and rolling-window stage routers (`P8a`) behave immediately post-compaction, and should context compaction automatically trigger a temporary frontier-model hold?
3. **Cross-Model In-Context Stylistic and Tool-Habit Contamination:** When a trajectory switches mid-task between models from different families (e.g., from DeepSeek V4 or Kimi K2.7 to Claude Opus 5.5 or GPT-6 Astra), the incoming model must condition on assistant messages and tool-call reasoning traces formatted in the prior model's distribution. Does cross-family prefix conditioning degrade pass rates relative to within-family tier switching (e.g., Haiku $\leftrightarrow$ Sonnet $\leftrightarrow$ Opus), and does that "cross-family friction tax" outweigh cross-provider price arbitrage?
4. **Online Continual Learning Under Partial Observability (Bandit Feedback):** As noted by [Scaling Conversational AI with Latency-Aware LLM Routing (arXiv:2610.26511)](https://arxiv.org/html/2610.26511v1), production routers observe outcomes *only* for the model they select, never the counterfactual models they did not select. How rapidly do online contextual-bandit routers suffer from confirmation bias or policy collapse when new models enter the catalog or repository workloads shift?
5. **Security and Governance Risks of Delegating Routing to External Decision APIs:** Sending full agent prefixes (which contain proprietary source code, internal file paths, and environment traces) to an external routing endpoint (such as [Not Diamond `modelSelect`](https://docs.notdiamond.ai/reference/token_model_select_v2_modelrouter_modelselect_post) or hosted decision models) expands the data-exfiltration and prompt-injection attack surface. Can a malicious repository file or GitHub issue text inject adversarial tokens that manipulate a semantic or System One router into downgrading security-critical verification steps to a weak model ("routing downgrade attack")?
6. **Joint Optimization of Skill/Tool Admission and Model Routing:** Recent work on evolving subtask-level routing and skills ([RSI-Router, arXiv:2609.34712](https://arxiv.org/html/2609.34712v1)) and tool-reduction harness effects ([Zhang et al., arXiv:2605.23950](https://arxiv.org/html/2605.23950v1)) indicates that pruning standing tool/skill definitions reduces context tokens and enables smaller models to succeed. Are **context/skill admission control** and **model routing** substitute levers or synergistic complements on the total-cost frontier?
