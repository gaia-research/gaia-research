## PR #326 — Cloudflare resilience

**Verdict: REQUEST CHANGES.** The design improves failure visibility, but does not establish a single deployment authority or that a green production workflow corresponds to the intended commit being live.

### Findings

1. **P1 — A successful check is mistaken for a live production revision** ([workflow lines 90–118](https://github.com/gaia-research/gaia-research/blob/95647f96e7926c60af2628fa51fd7654d95719a9/.github/workflows/cloudflare-deploy.yml#L90-L118), [smoke lines 166–205](https://github.com/gaia-research/gaia-research/blob/95647f96e7926c60af2628fa51fd7654d95719a9/.github/workflows/cloudflare-deploy.yml#L166-L205)). Any matching successful check causes Wrangler to be skipped; the four subsequent HTTP 200 checks do not identify the live Worker version, asset version, route content or `main` SHA. The Cloudflare bot's [PR #326 comment](https://github.com/gaia-research/gaia-research/pull/326#issuecomment-6714812786) explicitly identifies its successful head build as a **preview**, illustrating why a green check is not sufficient proof of production. An older production release can return 200 throughout while the summary says deduplicated and verified. Even a successful main build may no longer be the currently served version. Require authenticated authoritative deployed-version/SHA evidence (and account for propagation), rather than inferring revision from reachability. Distinguish dry-run/validation success from actual production release success at the check/status level as well as in prose.

2. **P1 — Two independent deploy authorities race** ([lines 36–38 and 98–128](https://github.com/gaia-research/gaia-research/blob/95647f96e7926c60af2628fa51fd7654d95719a9/.github/workflows/cloudflare-deploy.yml#L36-L38)). GitHub concurrency cannot lock Cloudflare Workers Builds. A missing/not-yet-created/queued check, a suppressed `gh api` failure, or a build still in progress after 60 seconds causes Wrangler to proceed while the Git integration can still deploy. Matching the app slug or check name does not prove target environment or current deployment. Disable the competing automatic production authority in Cloudflare, then verify the resulting configuration; do not claim deduplication as a lock.

3. **P1 — Manual recovery can deploy stale or unmerged code** ([lines 21–45](https://github.com/gaia-research/gaia-research/blob/95647f96e7926c60af2628fa51fd7654d95719a9/.github/workflows/cloudflare-deploy.yml#L21-L45)). Dispatch can select a ref and checkout uses it with the production environment; no guard ensures it equals current `main`. Reruns and queued runs can likewise publish older code after a newer `main`. A deliberate rollback is a different, explicitly authorized operation. Validate intended SHA against current main immediately before release, guard against stale runs and verify deployed SHA afterward.

4. **P2 — Concurrency and trigger coverage do not meet the handoff's guarantees.** GitHub concurrency with `cancel-in-progress: false` permits at most one running and one pending run; a new pending run replaces the existing pending run, not a strict FIFO queue. A dry run shares that group and can displace a pending real deployment. The `push.paths` filters omit `public/**` even though it contains deployable assets; an asset-only main change can be missed if the competing Cloudflare integration is disabled. Both the deploy and website CI paths require an inventory of all build inputs, including public assets. Ensure eventual reconciliation with the latest main even when runs are replaced.

5. **P2 — Recovery, retry and deployment correctness remain unproven.** Credentials are correctly required for a non-dry-run after build: missing/empty values cause exit 1. This validates presence, not token permissions. Three attempts with 10s then 20s waits are bounded, but retry **all** failures, not just transient ones; ambiguous remote success can lead to duplicate attempts. The dry run only builds/tests that `.open-next/worker.js` exists; it does not run Wrangler validation as its input description claims. Smoke requests have timeouts and retries but do not cover Agent Playbook, RSC or revision identity, and their overall time shares the 15-minute job timeout. Exercise missing credentials, failed and ambiguous deploys, recovery and timeouts in a safe non-production environment.

### OpenNext/Wrangler and configuration evidence

`npm run build` invokes OpenNext and `wrangler.jsonc` points to `.open-next/worker.js` plus `.open-next/assets` and the configured bindings. Inspecting the locally installed Wrangler/OpenNext code found Wrangler's OpenNext detection delegates `wrangler deploy` to `opennextjs-cloudflare deploy`, which populates applicable caches and then invokes Wrangler with recursion protection. Thus **do not assume** the raw command necessarily bypasses OpenNext with these pinned dependencies; actual CI deploy behavior, generated assets, required bindings and cache population have not been exercised. The config currently does not explicitly configure an incremental cache; assess it separately before changing storage.

Read-only GitHub API snapshot: repository secrets list only `GAIA_SKILL_TREE_RO_TOKEN`; no `CLOUDFLARE_API_TOKEN` or `CLOUDFLARE_ACCOUNT_ID` repository secret was listed. The environments list contains `github-pages`, not `production`. Organization-level secrets and access policies were not verified, so absence of usable credentials cannot be asserted conclusively. Before rollout, configure appropriately scoped credentials/account ID, an explicitly protected `production` environment and Actions token permissions; confirm branch protections and the intended release gate. Cloudflare dashboard Git triggers, production branch/service, bindings/routes, token scopes and deployed version were not independently accessible. Disable its competing production deploys rather than merely filtering PR builds; decide separately whether preview builds remain. GitHub Pages API reports source `main` root and status `built`; disabling obsolete Pages is an operator decision, not part of this review. The handoff also mentions a registry token rotation; its validity was not verified.

## PR #329 — Worker resource limits

**Verdict: REQUEST CHANGES**, independently of #326. The change plausibly reduces repeat parsing in a reused isolate, but the issue's diagnosis and production-fix claims are not established, and its tests do not verify the actual behavior.

### Findings

1. **P1 — Root cause and closure claim exceed the evidence** ([handoff §2](https://github.com/gaia-research/gaia-research/blob/9aea677cf22f4f8e0842bf370fd012e60f6d0417/docs/plans/issue-327-worker-resource-limits-handoff.md#L17-L34)). [Issue #327](https://github.com/gaia-research/gaia-research/issues/327) explicitly says the actual limit was not established from Cloudflare traces. The handoff provides no invocation IDs, logs, CPU/memory outcomes, deployed revisions, concurrency or reproducible commands to establish `exceededCpu`, `exceededMemory`, or a causal link. Heap allocation across parses is not peak live isolate memory; synchronous JavaScript parses cannot simply be counted as simultaneous within one isolate. Configured CPU limits and actual plan were not established. Do not state that this fixes #327, rules out other causes or prevents 500/503 without Worker traces and bounded before/after evidence. Keep issue open pending that evidence.

2. **P1 — Cold behavior and the actual serving path are unproven** ([page lines 25–29, 127–148](https://github.com/gaia-research/gaia-research/blob/9aea677cf22f4f8e0842bf370fd012e60f6d0417/app/research/orchestration-guide/page.tsx#L25-L29)). The route already uses `force-static` and `revalidate = false`. Determine from OpenNext build output and runtime traces whether requests hit prerendered assets/cache or execute this component before assuming per-request parsing. When executed, the initial parse remains synchronous and expensive; if a cold isolate is terminated before assignment, memoization cannot warm it. Isolates can be evicted or distributed; a warm-cache improvement is not a global guarantee. Validate cold and warm Worker requests and actual RSC prefetches, as well as unrelated routes, against pinned revisions.

3. **P2 — Regression tests do not call the real cache** ([test lines 9–55](https://github.com/gaia-research/gaia-research/blob/9aea677cf22f4f8e0842bf370fd012e60f6d0417/lib/orchestration-guide-memoization.test.ts#L9-L55)). The first test matches source text; the second directly compiles a different Markdown pipeline without the actual figure/table plugins or custom components, then repeatedly assigns a local variable. It does not call the page cache, count actual parses, render concurrent requests, compare output, measure heap, or test Worker runtime. Fixed wall-clock thresholds (>10 ms and <15 ms) can fail on fast or contended machines. Add behavioral cold/warm and parity tests on the actual pipeline, including custom figures, interactive components, HTML/RSC, and deploy freshness. `craft-ci` path filters exclude this changed `lib` test and page; no Vitest check ran on this PR head.

4. **P2 — Claimed quantitative gains and parity are unsupported.** The handoff supplies no benchmark script, hardware/runtime, sample distribution, raw outputs or parity artifact for 370 ms → 17 ms, 95.5%, 18×, zero heap churn or byte-identical HTML. These are not demonstrated by its test. Allocation and retained memory must be measured separately; caching a React tree retains memory per isolate, and React rendering/serialization work continues. The code is scoped to static bundled content, and synchronous initialization means one isolate cannot interleave initialization at an `await`; no user-specific content is apparent. That makes cross-request data leakage unlikely here, but React/RSC reuse and multi-request behavior remain untested. Module state is per isolate, not a distributed cache. Content changes require a new build/deployment; HMR/in-place content invalidation is not implemented, and old deployments/isolates may remain served during rollout or rollback.

### Independent verification and limits

On the checked-out #329 head with Node `v24.17.0`, `npx vitest run lib/orchestration-guide-memoization.test.ts lib/orchestration-guide.test.ts` passed **2 files, 5 tests**. This confirms those tests pass, not the cache or production claims above. CI pins Node 22, so the local runtime differs.

As a deliberately limited independent sanity measurement, five direct `react-markdown` parses of the checked-in guide using GFM, math and KaTeX, measured with Node `performance.now()` and `process.cpuUsage()`, produced wall/CPU ms respectively: `2055.7/2122.9`, `919.2/1028.3`, `1359.1/888.0`, `846.8/833.3`, `780.0/686.5`. This was a local Termux Node process, not Cloudflare, with neither production custom rehype plugins nor React render/serialization; it is not a before/after benchmark, a representative server measurement, or a refutation of the reported numbers on other hardware. It independently demonstrates nontrivial parse work in this environment only. No production or preview load test, Worker CPU/memory trace, heap profiling, HTML parity comparison, or deployment was performed.
